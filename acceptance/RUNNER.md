# Computer-control runner contract

You are verifying Director as Owner experiences it. Read this contract, the run manifest, each selected scenario, and [HOST_PROFILES.md](HOST_PROFILES.md) completely. Read docs/operating-agreement.md, docs/agent-task-tools.md and docs/dispatcher-manager.md for current behavior and supported diagnostics. Never use a past green run as current evidence.

The manifest's validated `target.profile` is authoritative. Do not infer it from the host, a Slack window, a service, or `DIRECTOR_CONFIG`. Existing scenario prose that names director-tests, director-feed-tests, config/director-tests.json, or state/testing/ is the Odyssey route label. For an Atlas or local manifest, use only its recorded source, feed, local config, state and service instead; do not manually substitute a different destination. This route substitution does not weaken any expected outcome, authorization, or cleanup requirement. A10/A11 on Atlas use the separate bounded procedure in HOST_PROFILES.md. The shared-receiver helper and service commands remain Odyssey-only; a local installation has no restart/outage authorization until its own reviewed procedure exists.

## Execute and observe

- Follow catalog order and dependencies. Use fresh screenshots/accessibility observations after layout changes; never blindly reuse old coordinates.
- Wait for Slack layout, scrolling and overlays to settle before evidence capture. Inspect the saved image for the channel/thread marker, relevant text and controls; retake unreadable or transient captures without discarding failure evidence. Capture menus/confirmation dialogs while open, then the settled resulting card/thread separately. A spinner, stale card or unrelated screen is not stable evidence.
- Drop is a two-step action: click the fixture's Drop button, inspect the confirmation title, then click Drop in the dialog. Keep it dismisses the dialog without cancelling. Do not mistake an open confirmation dialog for completed cancellation; cleanup also requires confirmation and durable-state verification.
- Record started_at before the first action. The default live reply budget is 120 seconds, receiver-owned received-checkmark budget 2 seconds, source-read/preparation budget 60 seconds, card budget 120 seconds. The checkmark means validated and durably saved; source-read/preparation and completion remain separate records. These are initial acceptance targets, not past performance claims. Timed maintenance scenarios use their stated windows. Capture actual elapsed time; exceeding a target is FAIL, even if a late response eventually arrives.
- Observe positive and negative assertions: the right reply AND no duplicate, waiting state AND no work triggered, navigation AND no implicit continuation.
- Capture a before/after screenshot for material UI transitions, open the actual response, and cross-check supporting source revisions, responsibility IDs, stable outgoing keys and jobs using the supported CLI/read-only diagnostics. Do not mark sources read/complete yourself to force success.
- Only use local fixtures/injection in scenarios labeled isolated/controlled. Annotate the intervention. An injected failure is not evidence of reproducing a real OS rejection.
- Assess every sentence in Expected. Record observations per assertion in the notes or an evidence log. FAIL means observed mismatch; BLOCKED means the behavior could not be tested. Do not treat screenshots existing on disk as proof they show the asserted behavior.
- Save evidence files beneath this run directory (0600). Evidence records have kind screenshot or log and a relative path. Computer/controlled PASS requires a screenshot; all PASS results require factual observations, start/end timestamps and cleanup=CLEAN.
- Finish cleanup even after a failed assertion. For shared A02/A03/A04 fixtures, record ownership transfer to A05; the run is not CLEAN until A05 or explicit teardown cancels the exact fixture. Verify no synthetic deferred work can resurface later. Leave labeled Slack history for provenance; don't delete real conversations.
- An active A04 real-timer wait may stay PENDING overnight, with A05 also PENDING. Retain its fixture and cleanup ownership: in results.json fixtures record cleanup=PENDING, scenario_id=A04, cleanup_owner and timezone-qualified resume_at, plus its exact IDs and due time. Keep A04 finished_at empty until observation completes. Report returns incomplete, never PASS/CLEAN. Resuming the same pinned run is permitted if target and runtime remain unchanged. Abandoning the run requires early-stop cleanup; an overnight wait with retained ownership is not abandonment.

## Failure → fix → re-test

Preserve the original failed attempt and evidence. Do not silently overwrite it with a passing result or retry until lucky. File a concrete bug or implement a scoped fix under the repository PR rules when authorized. Add/update a scenario and relevant code regression. Review and publish the fix, then initialize a fresh run pinned to the repaired SHA; rerun the failed scenario, its prerequisites and affected neighbors plus smoke. Link the old and new run IDs in notes. A blocked capability is not permission to bypass a device lock or approval rejection.

The tester may adapt navigation but may not weaken expectations, edit production state to obtain PASS, or call a unit test a UI test. Don't change product code during a run: that invalidates the pinned runtime. Stop, preserve the result, repair, and start a new run.
